# s3

One acquisition bucket per environment:
`address-lookup-<env>-acquisition-<account-id>`.

All buckets have versioning (Extraction and Upload pin to `versionId`), Block Public Access,
`BucketOwnerEnforced` ownership, SSE-S3 and a bucket policy denying requests without TLS.

| Prefix | Lifecycle |
| --- | --- |
| `control/acquisitions/` | Acquisition manifests expire after `audit_retention_days` (365). |
| `control/address-release/`, `control/receipts/`, `control/checksums/`, `control/ready/`, `control/reconciliation/` | No automatic expiry of operational state. |
| `landing/raw/` | Downloaded ZIPs expire after `landing_retention_days` (30). |
| `landing/extracted/` | Extracted CSVs expire after `landing_retention_days` (30). |
| `quarantine/` | No automatic expiry. Only the Quarantine role can modify objects; only the approved break-glass role can read them. |

Expiry creates delete markers in this versioned bucket. Noncurrent versions are permanently
deleted after the same retention period counted from when they became noncurrent, not from
original creation. Version pinning is supported within that retention window.

## Lambda permissions

Each Lambda has its own execution role, with separate read, write and prefix-scoped listing
statements. There is no bucket-wide object access and no delete permission.

| Role | Read | Write |
| --- | --- | --- |
| Discovery | Active cursor only | Cursor and acquisition manifests |
| Download | Acquisition manifests and its download receipts | Raw ZIPs, download receipts and raw checksum evidence |
| Extraction (`unzip`) | Raw ZIP versions and scan tags; extracted CSV versions for retry verification; its receipts and checksum evidence | Extracted CSVs, extraction receipts and extracted checksum evidence |
| Upload (`import`) | Acquisition manifests, ready evidence, its reconciliation cursor, extracted CSV versions and scan tags | Its reconciliation cursor only |
| Quarantine | Raw ZIPs, extracted CSVs and their tags as copy sources | Quarantine objects and copied tags only; it cannot read them back |

This group provisions storage and storage-scoped roles, not Lambda functions, triggers,
database grants or networking. Future Lambda deployment groups must use `lambda_role_arns`,
add their logging/networking/EventBridge permissions, and set `SOURCE_BUCKET`, `INGEST_BUCKET`
and `SCANNED_BUCKET` to the **same** `bucket_name` (also exposed as `lambda_environment`).
Scan is stateless and needs no S3 access.

GuardDuty protection plans **and** scan-event rules must include only the `scan_prefixes`
output: `landing/raw/` and `landing/extracted/`. Do not enable whole-bucket scanning.
Neither Control nor Quarantine is a scan input. This group does not deploy GuardDuty.
The Scan router rejects Control and Quarantine keys even if an event is delivered by mistake.
Control manifests do not require malware scan tags; payloads still do.

Supply the real, approved `break_glass_role_arn`; no placeholder role is trusted by default.
The role's owner must attach `break_glass_read_policy_arn` and retain their existing audited
assumption controls. This group deliberately does not create or change the break-glass trust
policy. Ordinary roles cannot list Quarantine or list the bucket root; always specify a
permitted `control/` or `landing/` prefix.

## Deployment and checks

The pipeline has `cidev-s3-plan` / `cidev-s3-apply` jobs. Set the Concourse secret
`secrets.address-lookup-cidev-quarantine-break-glass-role-arn` before installing the updated
pipeline. The apply job runs `test-deny-insecure-transport.sh cidev`: the same signed bucket
operation must succeed over HTTPS and return S3 `AccessDenied` over HTTP. The deployment
principal needs `sts:GetCallerIdentity` and `s3:GetBucketVersioning`.

Local checks (Terraform 1.7 or later for test overrides; deployments still support 1.3):

```sh
terraform init -backend=false
terraform validate
terraform test
```

The tests use fake credentials and override every managed resource. IAM policy JSON is
generated by the real provider, but no AWS resources are created, updated or deleted.

This changes the original three-bucket resource addresses and object-key layout. If that
configuration has already been applied, do not approve a destructive plan: migrate retained
objects and their version references deliberately before retiring the old buckets. This
configuration neither copies objects nor rewrites historical events or cursor contents.
