# Flyway database feed

`database/` is the single source of truth for the versioned schema and local
fixtures:

```text
database/
  config/
    flyway/
      common.conf
      local.conf
      production.conf
      staging.conf
      cidev.conf
    spring/
      local.properties
  migrations/
    schema/
      V2026.001__create_address_tables.sql
      V2026.002__create_os_control_schema.sql
      V2026.003__create_os_data_schema_and_tables.sql
      V2026.004__create_os_stage_schema_and_tables.sql
      V2026.005__create_address_lookup_view.sql
    local/
      V2026.006__create_local_seed_geometry_trigger.sql
      V2026.007__seed_gb_royalmailaddress.sql
      V2026.008__seed_gb_builtaddress.sql
      V2026.009__seed_isl_royalmailaddress.sql
      V2026.010__seed_isl_builtaddress.sql
  test-data/
    gb_royalmailaddress.csv
    gb_builtaddress.csv
    isl_royalmailaddress.csv
    isl_builtaddress.csv
  tools/
    generate_local_seed_sql.py
    package_db_schema.py
  version
```

The old Liquibase snapshot under
`address-lookup-api/src/main/resources/db/changelog/` is retained unchanged
for historical reference; it is not part of the active feed or API resources.
The Liquibase implementation that preceded this Flyway feed was not deployed
under the approved ALS-13 scope. Do not run the Flyway feed over an existing
database or copy Liquibase history into `flyway_schema_history`.

## Migration and database contract

Flyway Community 13.10.0 and PostgreSQL support are pinned in Maven. Every
migration has a unique numeric version and follows the standard `V...__...sql`
naming convention. Metadata comments retain the Jira, description, `team-atlas`
author, creation date, and source changeset/CSV mapping. Once released, a
migration is immutable; use a later forward migration for corrections.

Production locations contain schema migrations 001-005 only. Versions
2026.006-2026.010 are reserved for local geometry triggers and the four local
datasets. Future production migrations must use a version greater than
2026.010. Production configuration selects schema migrations only and cannot
load local fixtures by accident.

The version mapping preserves the prior Liquibase grouping:

| Flyway version | Prior source mapping |
| --- | --- |
| `2026.001` | `2026-001` changesets 01-07: address tables |
| `2026.002` | `2026-002` changesets 01-06: OS control schema and contracts |
| `2026.003` | `2026-003` changesets 01-11: OS data tables and indexes |
| `2026.004` | `2026-004` changesets 01-05: OS staging schema |
| `2026.005` | `2026-005` changesets 01-03: address lookup views |
| `2026.006` | `2026-006` changesets 01-06: local geometry triggers |
| `2026.007`-`2026.010` | Local fixture loads from the four named CSVs |

The old identity-bearing Liquibase source remains available in repository
history; the separately tagged original changelog snapshot is unchanged.

All configured environments use `public` as the explicit Flyway history and
default schema. Production SQL retains its explicit `os_control`, `os_data`,
`os_stage`, and `address_lookup` schemas; the public address-lookup view
preserves the existing API native-query contract. Flyway baseline and
out-of-order execution are disabled, migration naming and checksums are
validated, and `clean` is disabled. The approved target contract is an empty,
disposable PostGIS database; do not baseline a database or repair history to
hide drift.

The local-only migration generator consumes the committed CSV fixtures. It
validates fixture row counts, column names and widths, writes explicit column
lists, quotes values, maps the Liquibase `NULL` placeholder to SQL `NULL`, and
emits deterministic batches. The generated SQL is committed and must be
reviewed; it is not regenerated by the application or deployment runner:

```sh
python3 database/tools/generate_local_seed_sql.py
python3 database/tools/generate_local_seed_sql.py --check
```

The local trigger migration calculates GB geometry with SRID 27700 and ISL
geometry with SRID 4258 before loading the fixture rows. Expected counts are:

| Dataset table | Rows | SRID |
| --- | ---: | ---: |
| `os_data.add_gb_royalmailaddress_v1` | 99 | 27700 |
| `os_data.add_gb_builtaddress_v3` | 794 | 27700 |
| `os_data.add_isl_royalmailaddress_v1` | 126 | 4258 |
| `os_data.add_isl_builtaddress_v3` | 111 | 4258 |

The four seed migrations fail if their target table is not empty. They are for
disposable developer/test databases only.

## Spring runtime configuration

The nonlocal API configuration disables Flyway and keeps Hibernate DDL
generation off. Schema changes belong to a separately controlled deployment
runner, never API startup. The local profile explicitly imports
`database/config/spring/local.properties` and selects both migration
locations. The local resources are added to the API classpath only with the
`local-db` Maven profile; ordinary production API packages contain the schema
migrations only, not local fixture SQL, CSVs, or local datasource defaults.

From the repository root, with Docker available:

```sh
mvn -pl address-lookup-api -Plocal-db spring-boot:run \
  -Dspring-boot.run.profiles=local
curl "http://localhost:8080/address-lookup-api/addresses?postcode=WF2%207QD"
```

The Compose PostGIS database is exposed on port 5433. Use a fresh database
volume for this feed. Do not remove or reset a shared volume.

## Validation, archive, and recovery

```sh
make test-flyway
make package-db-schema version=2.0.0
```

`make test-flyway` checks deterministic CSV conversion, migration names and
metadata, Spring profile imports, Flyway discovery, fresh schema migration,
all fixture counts and geometry, repeat no-op behavior, malformed names,
duplicate versions, and checksum validation. It requires Docker and uses only
disposable PostGIS containers.

The production archive is `address-lookup-db-schema-2.0.0.zip`. It contains the
schema SQL, `database/version`, common and nonlocal Flyway configuration, and a
SHA-256 manifest. It excludes `migrations/local/`, `local.conf`, Spring local
properties, and all CSV fixtures. The archive packager discovers additional
well-formed schema migrations and rejects malformed or duplicate versions.

The separately owned runner loads common configuration before the selected
environment. For example, its production invocation supplies connection values
from deployment secrets rather than the feed:

```sh
flyway \
  -configFiles=database/config/flyway/common.conf,database/config/flyway/production.conf \
  -url="$SPRING_DATASOURCE_URL" \
  -user="$SPRING_DATASOURCE_USERNAME" \
  -password="$SPRING_DATASOURCE_PASSWORD" \
  migrate
```

This is the intended runner contract, not an executed deployment command.

Flyway Community does not include Undo migrations. Recovery is forward-only
correction or an approved backup/restore. Do not use `clean`, baseline, or
checksum repair to bypass an unknown schema state. Never rewrite a released
migration.

## Deployment handoff boundary

This checkout does not contain the production schema migrator or Concourse
pipeline configuration. The archive and CLI configuration are prepared for a
separate runner, but production rollout is not complete until its owner updates
that runner to Flyway 13.10.0, consumes only
`filesystem:database/migrations/schema`, supplies JDBC credentials from
deployment secrets, and verifies `public.flyway_schema_history` on the
approved fresh target. The nonlocal API remains migration-disabled. No live
database or deployment was changed during this implementation.
